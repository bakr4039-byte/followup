# Personal assignment approvals

`assignment-signing.js` adds the manager's **التكليفات** page and each employee's personal assignments. Import bundles contain private unsigned PDF bytes, a member identifier, a SHA-256 hash and signature rectangles; never commit bundles or employee documents to the public repository.

After validation against the private employee directory, one immutable request is published per employee and PDF hash. Re-import skips published requests and resumes incomplete uploads. The employee signs first, then the educational coordinator (directory member admin-2), then the principal (admin-1). The coordinator/principal's own assignments use two distinct signers. All approvals use personal employee UIDs, not the privileged platform manager identity.

Signers first view the PDF, then draw or upload their own PNG/JPEG/WebP signature. Images are decoded and normalized to a bounded PNG. A preview displays the signature at its assigned position. Explicit personal acknowledgement submits the image, original hash and server timestamp atomically with the counter. Firestore enforces UID ownership, ordering and immutable receipts.

The last approval triggers composition and private final-PDF storage. Every target and the platform manager can retry finalization after a network interruption. Until finalization, the request remains open; archived originals, receipts and PDF parts cannot be modified. Existing accountability and generic document signing flows remain unchanged.

Deploy the tested Firestore rules before importing. The rules grant each active recipient access only to their requests and completed PDFs. No outgoing messages or automatic signatures are generated.

Independent assignment titles remain active side by side for the same employee; only a newer request with the same owner and title supersedes a previous version. A bundle containing a deputy signature slot adds the active educational deputy (directory admin-3) between coordinator and principal. Existing three-signer assignments retain their original route.

Managers can open a prefilled WhatsApp message for the current unsigned recipient of each active assignment, or review all pending recipients matching the search. Phone numbers are loaded privately from the existing contact configuration and directory; public source contains no real contacts. Opening a WhatsApp link performs no database write. The manager must separately confirm actual sending before an immutable, server-timestamped notification record is created under the assignment. Records identify the confirming manager, current recipient/stage and PDF hash; Firestore rejects other senders, stale stages and mutations. These records represent manual confirmation, not WhatsApp delivery/read receipts. No WhatsApp message is sent automatically.

The manager dashboard summarizes only the latest version of each distinct assignment, with clickable signing-stage counts and a table/role ledger/card view. Live admin-only notification listeners reuse immutable WhatsApp confirmation records. Evidence must match the recipient, route stage and original PDF hash and include a server timestamp. Loading/error states never imply that a person was not notified; no record means only that no manual confirmation is stored. Per-role history shows confirmation dates and repeat-send counts. Dashboard totals exclude superseded versions, while the All view retains them for reference. No WhatsApp messages, signatures or notification confirmations are generated automatically.
